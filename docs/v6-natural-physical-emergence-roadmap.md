# AETERNA v6 Natural Physical Emergence Roadmap

## Purpose

This roadmap turns the v6 charter into an implementation order.
It is intentionally conservative.

AETERNA v6 must not jump directly to closure, organism-like behavior, or life-like visuals.
It must first close physical accounting paths and then observe whether candidate structures appear.

## Current starting point

The repository has reached v5.1.3 Drive-to-Wave Medium Transfer Skeleton.

Meaning:

- phase-carrying drive exists
- drive-side energy can be observed
- a checked drive-to-wave boundary exists
- requested coupling can be recorded
- effective coupling is still zero
- transferred energy is still zero
- wave medium mutation is still forbidden

The next phase is not v6.0 runtime physics yet.
The next phase is the v5.1.4 work-term preview.

## Phase 0: v6 charter / docs-only

### Goal

Freeze language, review rules, and implementation boundaries before runtime work.

### Allowed changes

- docs only
- roadmap updates
- guardrail updates
- no runtime imports
- no tests required beyond documentation-sensitive checks if present

### Forbidden changes

- no runtime behavior changes
- no medium mutation
- no new physical coupling
- no `AeternaNetwork` changes
- no UI life claims

### Completion condition

The repository contains a clear v6 charter and roadmap that future agents can follow without interpreting v6 as a life-simulation or visual-performance phase.

## Phase 1: v6 guardrails / docs-only

### Goal

Make v6-specific forbidden naming and result-coded implementation patterns explicit.

### Allowed changes

- add or update docs listing forbidden identifiers
- add lightweight documentation tests only if the repository already supports them

### Forbidden changes

- no runtime behavior changes
- no renaming of existing runtime identifiers unless isolated and separately reviewed

### Completion condition

Future PRs have a documented checklist for avoiding result-coded coherence, life metaphors, and hidden designer intervention.

## Phase 2: v5.1.4 Drive-to-Wave Work Term Preview

### Goal

Compute a preview of nonzero drive-to-wave work without mutating the wave medium.

### Allowed changes

- introduce a preview report
- compute candidate effective coupling in a separate preview path
- compute candidate work term
- compare drive-side candidate work against medium energy snapshots
- emit diagnostics when preview work is nonzero but not applied

### Forbidden changes

- do not mutate the wave medium
- do not apply effective coupling to runtime dynamics
- do not inject into center buffer
- do not claim coherence, life, or closure

### Completion condition

The preview explains what would be transferred if applied, while proving that the actual medium state remains unchanged.

## Phase 3: v5.1.5 Applied Transfer with Ledger

### Goal

Apply a small nonzero drive-to-wave transfer with explicit energy accounting.

### Allowed changes

- config-visible effective coupling
- small nonzero default only if tests cover zero and nonzero modes
- explicit work term
- medium energy delta accounting
- residual reporting

### Forbidden changes

- no direct center-buffer injection
- no hidden dissipation
- no unaccounted clamp loss
- no coherence booster
- no life metaphor

### Completion condition

A small applied transfer closes a ledger:

```text
drive_work = medium_energy_delta + dissipation + residue + outflow ± residual
```

If some terms are not yet represented, they must be explicitly zero or diagnostic, not hidden.

## Phase 4: v5.1.6 Transfer Scenario Suite

### Goal

Validate the transfer path across reference scenarios.

### Required scenarios

- zero coupling
- small coupling
- high damping
- zero drive amplitude
- masked drive
- unmasked drive warning
- non-finite sample warning
- residual stress case

### Completion condition

The suite reports both successful and failed conditions. A scenario may fail physically, but it must not fail silently.

## Future v7: Autocatalytic / Inheritance / Selection Track

v6 and Phase H can build a vessel and test whether closure-like candidates are natural.
They do not yet establish primitive life.

Future v7 should examine:

- whether one closure cycle increases the likelihood of another
- whether local parameters are retained, transported, or inherited
- whether multiple structures compete for limited drive/resource
- whether similar structures re-form elsewhere
- whether selection-like persistence occurs without a selector

These are future research phases, not v6 claims.
