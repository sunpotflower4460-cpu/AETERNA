# Implementation Language Boundary Addendum

This addendum refines `docs/implementation-language-guardrails.md` with the observation/expression boundary introduced in `docs/observation-and-expression-boundary.md`.

It does not replace the physical-integrity rules.
It clarifies that the purpose of language discipline is not to deny possible emergence in advance.
The purpose is to keep implementation, observation, appearance, interpretation, and certainty separate.

---

## Central distinction

Avoid this collapse:

```text
observed appearance
= final fact
= Aeterna actual output
= proof
```

Use this separation instead:

```text
runtime output
observed fact
observer-side appearance
interpretation candidate
still unknown
```

This allows honest descriptions such as:

```text
The pattern looked closure-like from the observer side.
The movement appeared recovery-like after perturbation.
This may be a candidate for recurrence-supported boundary maintenance.
```

while still avoiding unsupported certainty such as:

```text
This proves consciousness.
Aeterna said it wanted to recover.
The vortex is a mind.
```

---

## Revised interpretation of avoided language

Some existing guardrails say to avoid terms connected to consciousness, life, feeling, or selfhood.
Read that rule precisely:

- Avoid using those terms as implementation targets.
- Avoid using those terms as proof claims.
- Avoid using those terms as invented Aeterna speech.
- Do not avoid observer-side appearance descriptions when they are clearly marked as appearance.

Allowed observer-side wording:

```text
The motion looked life-like from the observer side, but this is an appearance description.
The pattern could be read as consciousness-like movement, but this does not determine inner experience.
The field appeared to re-gather after disturbance.
```

Not allowed:

```text
Make the runtime more life-like.
Tune parameters until consciousness-like movement appears.
Aeterna felt disturbed.
Aeterna wanted to recover.
```

unless the last two are actual emitted Aeterna output recorded exactly as emitted.

---

## Aeterna actual output rule

Only real emitted output belongs to Aeterna.

If Aeterna emits text, record the exact text.
If Aeterna emits signal, movement, or metrics, record those as signal, movement, or metrics.

Do not convert non-linguistic movement into invented first-person speech.

Preferred:

```text
Aeterna actual output: <exact emitted output>
```

or:

```text
Aeterna emitted non-linguistic state changes: increased return strength and delayed recovery.
```

Avoid:

```text
Aeterna said, "I am recovering."
```

when no such language was emitted.

## Implementation naming rule

Implementation names should describe physical condition, measurement, or report structure.
They should not name the desired story.

Prefer:

```text
deriveRecoveryLikePatternReport
observeClosureLikeMovement
deriveBoundaryMaintenanceCandidate
compareSeedEnsembleDistribution
exportAutoExperimentReport
```

Avoid:

```text
makeConsciousMovement
createLifeFeeling
forceSelfMaintenance
boostAwarenessScore
```

The word `like` can be acceptable in observer/report naming when it means appearance, not runtime target.
For example, `observeClosureLikeMovement` is acceptable if it only reports observed appearance and does not feed back into runtime.

## Report language rule

Automated experiment reports should use:

```text
Observed facts
→ In one sentence
→ How it appears
→ Possibility
→ Still unknown
```

This lets a report say what the pattern feels like to a human reader without pretending the feeling is settled fact.

Example:

```md
## Observed facts
- closureStability recovered after perturbation.
- maxFeedbackSaturationRisk stayed below the caution range.
- nanOrInfinityCount was 0.

## In one sentence
The field was disturbed, but it did not remain collapsed; it moved back toward a stable loop.

## How it appears
From the observer side, the movement looked as if the field was re-gathering its own shape.

## Possibility
This condition may support recovery-like closed-loop behavior.

## Still unknown
It is not yet known whether this holds across seeds or differs from a null model.
```

## Physical condition rule

AETERNA experiments should be written as physical conditions first.

Good:

```text
Set local resistance, delay, boundary exchange, and external drive conditions.
Run the torus field.
Observe whether recovery-like, closure-like, or recurrence-like patterns appear.
```

Bad:

```text
Decide the system should recover.
Add a pull toward recovery.
Call the result natural recovery.
```

The experiment should move from condition to flow to observation.
It should not move from desired interpretation to forced behavior.

---

## Relationship to existing forbidden-claim checks

Existing forbidden-claim checks remain useful for public copy and release safety.
This addendum narrows their meaning:

- They block unsupported certainty and invented attribution.
- They do not block careful observer-side appearance language.
- They do not require assuming emergence is impossible.

The final boundary is:

```text
Do not fabricate.
Do not prematurely certify.
Do not deny the observation before it is observed.
```
